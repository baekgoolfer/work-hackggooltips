# Security policy

## Reporting a vulnerability

**Report privately, not in a public issue.** Use GitHub's private vulnerability reporting:

1. Open the repository's **Security** tab.
2. Choose **Report a vulnerability**.
3. Describe what you found, the version or commit, your macOS version and chip, and the steps to reproduce it.

Only the maintainers can see the report. Do not attach recordings, transcripts, notes, meeting titles, real logs or real API keys. A synthetic reproduction is enough; if you need to show a log, remove everything that identifies a person or a meeting (`LOG_CONTENT=0` keeps most of it out of the logs).

This project is maintained by volunteers. There is no guaranteed response time and there is no bug bounty. We will acknowledge a report when we can, work with you on a fix, credit you if you want, and ask for a reasonable time to ship the fix before you disclose it publicly.

## Supported versions

Only the latest tagged release and the default branch receive fixes. This is an experimental project (see the status in the [README](README.md)).

## What counts as a security problem

- A secret leaking: the Anthropic API key (or key-shaped text) in a log, file, command line, `state.json`, `usage.jsonl`, a session folder or the environment of a process other than the `claude` call; a failure of the redaction.
- Audio, transcript text, meeting titles or calendar data leaving the Mac outside the documented paths ([docs/PRIVACY_AND_CONSENT.md](docs/PRIVACY_AND_CONSENT.md)), for example a **local-only** meeting that still uses a lane (Claude, calendar, archive upload, external speech engine).
- A way around the gate that keeps the login agent from being written or loaded before the live test was confirmed, or a recording that starts or continues when it should not.
- Command injection, path traversal or unsafe file handling in the scripts or the pipeline, for example through a meeting title, a vocabulary line, a `config.env` value or a file name.
- Unsafe handling of privileges in the install, signing or packaging scripts.

Not in scope: recording people without their consent (that is misuse of the tool, see the legal notice in the README); what Anthropic, Google or another service does with the data you send them; weaknesses of third-party packages (report them upstream, and tell us if our pinned version is affected); anything that needs an attacker who already runs code as your user.

## The security model in brief

- The app runs as you, with the macOS permissions you grant it: Microphone, System Audio Recording, Notifications, and Chrome Automation only if you enable Google Meet detection or `CALL_BROWSER_URLS` (meeting pages of other sites in Chrome; both are off by default). While a meeting is processed, its recording lives in `~/Library/Application Support/MeetingCapture`; the staging and local-archive folders are excluded from Time Machine backups.
- **API key.** In `CLAUDE_AUTH=api` mode the key lives only in the macOS Keychain. It is read just before a call and passed to the `claude` process only as the environment variable `ANTHROPIC_API_KEY`; never on a command line, never written to a file. The environment of that process is an allow-list. Key-shaped text is redacted from logs and state files. The project does not read or store your Claude login tokens.
- **Settings window (API keys and `config.env`).** The window stores the Anthropic key and the keys of the CLOVA and OpenAI-compatible engines only in the macOS Keychain, with `/usr/bin/security -i` (the command on stdin, the value hex-encoded: no argument, no environment variable, no file, no log), under the service and account strings the pipeline reads; it shows only "Stored in Keychain" or "Not stored" and reads a stored key back once to confirm it. Swift cannot wipe a `String`, so a typed key stays in the process's memory until it is reused. It writes `config.env` (never a secret) atomically with mode 0600 and a backup, refuses values the parsers would misread (line breaks, comment triggers, quotes at the edges, a value that looks like another `KEY=VALUE` line, a key that is not an upper-case key name) and refuses to touch a file that is not UTF-8 or has unusual line separators. The consent to a cloud speech engine and the Google sign-in are never written by it: it only opens Terminal with the existing command. A bug in any of this (a key in a log, an argument or a file, a consent written without the typed sentence, a `config.env` line that changes meaning) is in scope. No test used the real Keychain. See [docs/SETTINGS.md](docs/SETTINGS.md).
- **Network.** The pipeline talks to Anthropic through the `claude` tool; the install downloads from PyPI, Hugging Face and GitHub. External speech engines (a company server, Azure Speech, NAVER CLOVA Speech, or an OpenAI-style server at an address you choose) are an opt-in, also on a personal install: you name one in `ASR_ENGINE` or `ASR_FALLBACK` and type a consent that binds its host and port, and an organisation policy can restrict them. They go through a guarded client that only talks to that host (https, no redirects) and sends speech, the API key you stored for it and, for CLOVA, vocabulary terms; docs/PRIVACY_AND_CONSENT.md lists it. For the OpenAI-style engine the host is your choice and the project cannot check who runs it.
- **Calls of other apps (`CALL_DETECT`).** The table of known call apps (including personal messengers such as FaceTime, WhatsApp, KakaoTalk and Discord) is on by default; guessing any other GUI app (`CALL_DETECT=generic`) is opt-in. The detection reads only Core Audio process flags (which process has an input or output running): no stream is opened, no title or window is read. Your per-app decisions live in `~/Library/Application Support/MeetingCapture/call-apps.json` (mode 0600, written atomically, bundle ids and names only). The "never record" list fails closed: a file that cannot be read pauses every call of another app and is never overwritten, a decision text that is not `allowed` reads as `denied`, and a decision whose write fails stays in force until the app quits. `ENABLED_PLATFORMS` does not limit these calls; `CALL_DETECT` does, and an organisation policy can set or enforce it (on a Mac with a policy an unset value is `off`).
- **App installer (disk image, `docs/DISTRIBUTE.md`).** The image holds the app with a Python runtime archive inside. It is signed with its builder's own self-signed identity, not notarized, without the hardened runtime: macOS warns at the first open, and anyone who can change the app in Applications can change everything in it. `scripts/fetch_python_runtime.sh` keeps the runtime only when its sha256 is the one the builder pinned in `scripts/python-runtime.lock`; `scripts/first_run_install.sh` checks the archive against the sha256 in the app's own `components.json` before it unpacks it (that shows the archive is the one put in the app, not who put it there: the signature does). The helper runs as you in Terminal, never with `sudo` or `launchctl`, installs no login item and never runs the macOS `security` tool itself. Its Python child does (`python -m mcap api-key ...`): step 4 asks `api-key status --exists`, which runs `security find-generic-password` without `-w` (the item's attributes only: the stored value is not read and no Keychain dialog can appear); the Anthropic key is typed into the macOS `security` tool by `python -m mcap api-key set` (no script, argument, environment variable or file of the helper sees it), and `api-key set` reads the item back once to report its length and whether it starts with `sk-ant-` (the value is never printed or stored). Packages are version-pinned (hash-pinned only with a hash lock: `scripts/build_dmg.sh` compares a given lock with `pipeline/requirements.lock.txt` at build time, warns when there is none and fails with `--require-hash-lock`) and the models are checked against pinned sha256 values by `scripts/setup_python.sh`, as in the developer install. Only one helper window runs at a time (a lock link `.first-run.lock` in the Application Support folder that names the pid of the run; a second window stops and changes nothing; a lock of a dead or foreign process is ignored). Until the helper has finished (no `components-installed.json`) the app records nothing: it detects no call, ignores "Start Recording Now" and the calendar auto-start, because the recording legal notice is shown only by the helper; this is a guard against recording before the notice, not a security boundary: the record is a plain file that any process running as you can create. The helper copy and `first-run.env` live in your Application Support folder (any process of yours can write there; the app rewrites the copy from the bundle each time, `first-run.env` is read as text, never run). The consent to a cloud speech engine stays a Terminal-only step. Not verified on a clean Mac.
- **Login agent gate.** The app is only set to start at login after you confirmed the live test yourself (`make confirm-live-tested`). That is a safety gate against recording by accident, not a security boundary: it is a plain file that any process running as you could create.
- **Optional fixed signing identity** (`scripts/make_signing_identity.sh`). The self-signed private key sits in your login keychain and `/usr/bin/codesign` may use it without a prompt, so any process running as you can sign code with it; code signed with it inherits the permissions you granted the app; the app is signed without the hardened runtime, so a process running as you can inject a library into it. The default ad-hoc signing has none of these properties. Details: [docs/INSTALL.md](docs/INSTALL.md).
- **Not a defence** against malware that already runs as your user: it can read your recordings and files like any other process of yours.
- Some test fixtures contain obviously fake or throw-away key material (under `pipeline/tests/`). They protect nothing; secret scanners may flag them.
